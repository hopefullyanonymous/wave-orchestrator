## P1-1 — §Recovery: the "close-out unfinished" row can never fire (shadowed)

- `references/protocol.md:235` ("Rows are matched top to bottom; the first match wins"),
  rows at `references/protocol.md:251` and `references/protocol.md:252`; mirrored at
  `templates/00-READBEFORE.md:263`, rows at `templates/00-READBEFORE.md:279-280`.
- The row `🟢 | branch ancestor … | Correct state — waits for its covering checkpoint`
  sits directly above `🟢 (every member of a checkpoint-carrying wave is 🟢, ⛔ or 👤) |
  checkpoint row not 🧪/✅ | Close-out unfinished → finish it …; never open the next
  wave`. For a 🟢 row, "branch NOT an ancestor" (row above) and "branch ancestor"
  exhaust every git state, so the close-out row is unreachable — not just deprioritized.
- **Scenario**: a checkpoint-carrying wave finishes integrating; the orchestrator starts
  close-out (tip validation, QA pre-smoke) and the session dies before the single
  close-out commit. Next session reconciles every batch row as "Correct state — waits
  for its covering checkpoint". No 🧪 exists, and the wave-open guard ("no reached
  checkpoint is unanswered") never fires because the checkpoint row is still ⬜, which
  the PROGRESS legend defines as "not reached". Step 4 opens the next wave and the
  checkpoint is silently skipped — the exact outcome the dead row exists to prevent, and
  a direct violation of "a reached checkpoint is never skipped". If it was the FINAL
  checkpoint, no ⬜ batches remain and the session algorithm has no defined move at all.
- **Fix**: hoist the close-out-unfinished row above both 🟢 rows — the same move the
  eighth review made for the capped-marker row. Note the row's own verdict must also
  cover P1-3 below, or the fix only half-works.

## P1-3 — In-flight (uncapped) repairs are invisible to §Recovery

- A failed pre-smoke step "keeps rows 🟢" (`references/protocol.md:202`) and writes a
  Notes marker only when *capped*. The `fix/<batch>-presmoke-<step>` branch belongs to
  no reconcile row: the batch row is 🟢, and no row keys on the repair branch.
- **Scenario**: pre-smoke fails, the repair mini-batch is spawned, session crashes.
  Resume reconciles the 🟢 rows as "correct state"; nothing anywhere records that a
  repair is outstanding. Combined with P1-1 the next wave opens over a known-failing
  smoke step; if the close-out is later resumed, pre-smoke re-runs, fails again, and
  re-spawns a same-named branch (`git branch` collision with the orphaned one).
  The `-tip` variant is half self-healing (resume-time validation re-detects the red
  tip) but still re-spawns `fix/<batch>-tip` over the crashed attempt's branch.
- **Fix**: write `presmoke repair pending: <branch>` / `tip repair pending: <branch>`
  into the affected row's Notes at spawn time (mirroring the existing `… capped:`
  markers), and key a reconcile row on them.

## P1-4 — No §Recovery row matches a plain ⬜; a crash mid-wave-open orphans branches

- The gather step covers every row not ✅/👤/⛔(dropped), but the table has no ⬜ entry.
  Step 4 cuts every member branch and creates every worktree, and only *then* commits
  the wave-open flip; per-worktree setup can take minutes, so the window is real.
- **Scenario**: crash after branches/worktrees exist but before the wave-open commit.
  Resume reconciles nothing (⬜ rows match no row), step 4 re-runs, and
  `git branch <batch-branch>` fails: branch already exists. The contract gives no
  ruling; the driver improvises with a half-provisioned wave.
- **Fix**: make wave-open idempotent (adopt branches/worktrees that match the plan when
  their tip equals the wave base, else stop and investigate), or add an

### F1 — Re-issued smoke pages can present old passes as current-build results — FIXED (2026-09-18)

- **Resolution**: verdicts now retain their build SHA and step revision in localStorage
  and the artifact database. Re-issues label unaffected verdicts as carried over;
  affected steps return to the run list and copy as `NOT RE-RUN` until a fresh verdict
  or applicable agent verification. Notes and unaffected passes survive. Re-selecting
  a verdict records the current build/revision; editing a note does not. Protocol,
  generated contract, and smoke-page instructions agree. Regression coverage:
  `node --test tests/smoke-page.test.cjs`.
- **Residual validation gaps fixed**: agent evidence now records its tested step
  revision. Stale or incomplete evidence cannot mark a step done; unchanged evidence
  from an earlier build is explicitly labeled carried-over. An invalid/unfilled
  `BUILD_SHA` visibly stops verdict collection and copying before any storage access;
  invalid SHAs in saved verdicts cannot count as current or carried-over results.
  Regression cases cover both failures, same-build step corrections, short agent
  SHAs, unchanged evidence, and untouched storage on rejection.
- Original assessment below retained for context.

- Mechanism as claimed, all confirmed: storage keys on checkpoint only
  (`smoke-page-template.html`, `{{CKPT_KEY}}-run` / `{{CKPT_KEY}}-steps`), nothing binds
  a verdict to a build SHA; on re-issue "earlier verdicts survive"
  (`protocol.md:278`, `00-READBEFORE.md:305`); "Jump to first unmarked" skips any step
  carrying a status (`smoke-page-template.html:1110-1121`), and "Copy results" renders
  a surviving `PASS` under the new `{{COPY_HEADER}}` version with no annotation.
- **Overstated**: the default flow annotates affected steps and names the step numbers
  to re-run (`smoke-page.md` §Corrections), which lands the old pass as "PASS — <old
  note>" under an aside that says a fix touched the step — visible, not silent. The
  claim's scenario is real specifically when the user ignores that and returns an
  untouched old pass as their re-verdict, and intake then counts it. Mitigations to keep
  intact: the PATCH bump + step-0 gate (`00-READBEFORE.md:308-310`) defeat the worse
  failure (running the re-issue against the OLD build), and the committed
  `smoke-<Cn>.html` preserves what was actually handed over.
- **Disposition**: keep as a hardening item, downgraded — on fix-up re-issue, re-render
  surviving non-re-run verdicts in the copied text as `PASS (carried over, pre-repair
  build)`; optionally include the run's integration SHA in `{{COPY_HEADER}}`. Do NOT
  blanket-invalidate verdicts on republish — that breaks the checkpoint-owned-by-the-user
  property for unaffected steps.

### F2 — Server synchronization can erase a newer local failure — FIXED (2026-09-18)

- **Resolution**: local verdict changes, clears, and note edits now record a monotonic
  per-step `at` immediately; database writes retain it. Snapshots only replace a
  record with a strictly newer timestamp and do not rewrite localStorage when nothing
  changed. Active note editing defers the whole remote record until blur, avoiding
  mixed verdict/note/provenance. Tests cover delayed passes after failures and clears,
  reload, equal/missing/malformed timestamps, debounced notes, newer remote updates,
  and continued typing after a deferred update. Validation:
  `node --test tests/smoke-page.test.cjs`.
- Original assessment below retained for context.

- Confirmed against `smoke-page-template.html:1184-1208`: the `onSnapshot` handler
  overwrites `local[n]` with the server doc unconditionally (only the note survives, and
  only while the user is actively typing in that textarea), then `saveLocal()` persists
  the server state into localStorage. The doc stores `at` but no reader compares it;
  local records carry no timestamp at all — no recency comparison is possible on either
  side. A stale snapshot (offline session resuming with a cached listener, second
  device) reverts a newer local FAIL to an old PASS, and the overwrite is written back
  to localStorage, so it survives reload.
- Exposure is genuinely narrow (single-user artifact, per-step writes), so P2 is right;
  but this is the page that exists to collect verdicts — silent verdict loss is
  correctness, not polish.
- **Fix**: stamp local writes (`at`), ignore snapshot docs whose `at` is older than the
  local record's, and never `saveLocal()` a snapshot that changed nothing local.

### F3 — Discovery misses custom integration branches when any conventional branch exists — FIXED (2026-09-18)

- **Resolution**: Discovery now enumerates every local and remote-tracking branch,
  skips only symbolic refs, and probes each remaining tree regardless
  of branch naming or earlier matches. Full refs avoid name collisions; duplicate
  ledger ids are grouped across branch copies, with ambiguous ownership surfaced.
  F5 below removes the original fix's ancestry pre-filter and defines target-based
  reconciliation only after discovery.
- **Original F3 validation** (before F5): an isolated Git fixture found conventional, custom, shallow, and
  remote-only ledgers together; grouped duplicate branch copies; skipped symbolic
  and merged refs; excluded archive-only content; and left checkout/index unchanged.
- Original assessment below retained for context.

- The "already-merged stale ledger suppresses the fallback" chain fails as written:
  step 2 skips branches that are ancestors of the default branch *before* any
  classification (`SKILL.md` Discovery step 2, the `merge-base --is-ancestor` skip), so
  the reproduce case's stale merged branch never reaches discovery output.
- **Confirmed kernel**: the glob `'refs/heads/**/*-ledger'` matching *anything live*
  (e.g. a second, genuinely active `chore/x-ledger`) suppresses the ls-tree fallback
  entirely, so an active ledger on a custom-named branch (`feature/big-change`) is never
  discovered. Real gap, narrower trigger than claimed. Also worth noting in passing:
  the glob would miss a custom branch whose name *ends* in `-ledger` but lives at a
  shallow ref depth (`refs/heads/foo-ledger` — the `**/` requires an intermediate
  directory).
- **Fix**: drop the glob-gates-fallback structure; run the ls-tree probe over every
  head not already matched and not an ancestor of the default branch (or make the glob
  advisory-only). Cost is bounded by head count and the probe is read-only.

### F5 — Default-branch guesses can hide ledgers and corrupt shipment recovery — FIXED (2026-09-18)

- **Finding**: `{{MAIN_BRANCH}}` already existed and was baked into each generated
  contract, but both scaffolding definitions fell back to the current checkout. A
  feature branch captured there could become both the wrong protected branch and a
  false-positive shipment target. Discovery separately used an unresolved `<default>`
  as an ancestry pre-filter. Both defects predate the F3 fix; `init.defaultBranch`
  is an initialization preference and is not a safe replacement fallback.
- **Resolution**: discovery probes every non-symbolic ref before classifying a ledger.
  Recorded target evidence can identify completed/archived stale copies afterward;
  stale-copy proof uses the ledger's last-changing commit and subtree identity, not
  whole-branch ancestry, so unrelated later work cannot resurrect an archived ledger.
  Recorded corrections in the owning contract supersede proven older target values;
  unresolved conflicts and uncommitted ledger edits remain visible. Ancestry alone
  cannot establish completion. Interview #4 confirms the full protected local default ref
  and whether shipment means a local merge or a merge on a named remote, with the
  exact branch on that source baked into the contract. Remote shipment requires a
  fresh read-only query and a locally available commit for ancestry; unavailable or
  ambiguous evidence never flips rows or authorizes cleanup. Existing unambiguous
  contract semantics are preserved, and contract-less legacy targets must be resolved
  explicitly rather than guessed.
- **Validation**: current templates use 41 registered placeholders; the registry has
  44 rows, with only the three naming-only values absent from templates. All 26
  Recovery rows match after integration-name normalization; `git diff --check` passes.
  Isolated Git scenarios cover discovery without `origin/HEAD`, conflicting
  main/master hints, local versus remote containment, and unavailable remote objects.
  Adversarial review added completed/archive copies on unrelated-work branches and
  retained old contract copies after a recorded target correction.
  These Git assumptions are now repeatable in `tests/git-contract.test.cjs`, including
  negative cases for missing objects, newer ledger commits and uncommitted ledger edits.

### OS-BL-003 — ASK — A ledger evidence path exceeds Git's default path limit on Windows

- `.agents/changes/OS-20260918-readonly-evidence-smoke-inputs/evidence/C1/inputs/issue-001/recursive-discovery/tests/unit/discovery-sentinel.test.cjs`
- With `core.longpaths` unset, Git cannot stat this file: every `git diff`,
  `git diff --check` and `git status` prints `Filename too long` to stderr while still
  exiting 0, and the path is listed under `git diff --name-only HEAD`. The file itself is
  NOT modified — index, HEAD and each relevant commit carry the same blob, and the
  on-disk bytes match it.
- **Scenario**: the noise is harmless, but the same length blocks `git worktree add` into
  any longer root. It did: creating a base-probe worktree under the session scratchpad
  aborted with `Filename too long` on this and sibling paths, and both the step-10 and
  step-00 repairs had to use deliberately short worktree roots. A future session that
  assumes the scratchpad works will hit the same wall.
- **Fix when touched**: `git config core.longpaths true` for the repository, or shorten
  the checked-in evidence path. Left alone here on purpose — changing Git configuration
  is outside every fence in that ledger and is the repository owner's call.
